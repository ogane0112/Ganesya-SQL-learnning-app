# SQL学習アプリ 要件定義書

**version 0.1（ドラフト）**
**作成日：2026年8月12日**

---

## 1. 概要

### 1.1 目的
ブラウザ上でSQLを実際に書いて実行しながら学習できるWebアプリケーションを提供する。
サーバー側にDBを持たず、学習用SQLは**クライアントサイド（ブラウザ内）で実行**することで、低コスト・低レイテンシ・高いセキュリティ性を実現する。

### 1.2 スコープ
- SQL学習コンテンツ（問題・お題データ）の閲覧
- ブラウザ内でのSQLエディタ・実行環境の提供
- ユーザー認証（ID/パスワード、パスキー）
- 学習進捗の保存・管理
- インフラは全面的にCloudflareで構築

### 1.3 想定ユーザー
- SQLを初めて学ぶ学習者（学生・エンジニア志望者・業務でSQLが必要な非エンジニア等）

## 3. 採用技術と選定理由

| レイヤー | 技術 | 選定理由 |
|---|---|---|
| ホスティング | **Cloudflare Pages** | 静的SPAをCloudflareのエッジで直接配信。Workersとの統合がシームレス |
| API/バックエンド | **Cloudflare Workers** | Pagesと同一プラットフォームでエッジ実行。認証・進捗APIをサーバーレスで実装 |
| DB（サーバー側） | **Cloudflare D1**（SQLiteベース） | Cloudflareネイティブ、無料枠あり、Workersからの低レイテンシアクセス。SQLiteのため学習アプリのドメインとも親和性が高い |
| KVストア | **Cloudflare KV** | セッション情報・レート制限など低頻度更新データの高速参照に最適 |
| クライアントSQL実行エンジン | **sql.js**（SQLite WASM）※代替: wa-sqlite | ブラウザ内で完結してSQLを実行可能。サーバー側にDB接続不要でセキュア＆低コスト |
| SQLエディタUI | **CodeMirror 6**（SQL構文ハイライト・補完） | 軽量、拡張性が高く、Web標準に強い |
| フロントエンドFW | **React + Vite**（Cloudflare Pages対応） | Cloudflare Pagesのビルド環境との相性が良く、静的ビルド出力がシンプル |
| 認証（パスワード） | Workers上でPBKDF2/bcrypt相当のハッシュ化（Web Crypto API） | Node依存ライブラリを避け、Workers Runtime標準APIで完結 |
| 認証（パスキー） | **WebAuthn** + `@simplewebauthn/server`（Workers対応）, `@simplewebauthn/browser` | パスキーの業界標準実装。Cloudflare Workers上での動作実績あり |
| セッション管理 | JWT（署名）+ Cloudflare KVでの失効管理 | Workersはステートレスなため、署名付きトークン＋KVでの補助管理が定石 |
| CDN/セキュリティ | Cloudflareの標準機能（WAF, Bot Management, Rate Limiting） | インフラ全体がCloudflareのため追加設定なしで享受可能 |

## 4. 機能要件

### 4.1 SQL学習・実行機能
| ID | 要件 |
|---|---|
| F-01 | ユーザーはブラウザ上のSQLエディタにSQL文を入力できる |
| F-02 | 入力したSQLは**クライアントサイド（ブラウザ内のWASM SQLiteエンジン）**で実行され、サーバーへは送信しない |
| F-03 | 各問題ごとに、あらかじめ用意されたサンプルデータ（テーブル定義＋初期データ）をブラウザ内DBに読み込む |
| F-04 | 実行結果をテーブル形式で表示する |
| F-05 | SQLエラー発生時、エラーメッセージを分かりやすく表示する |
| F-06 | 正誤判定（想定結果と実行結果の比較）をクライアントサイドで行う |
| F-07 | SELECT / INSERT / UPDATE / DELETE / JOIN / GROUP BY 等、主要構文を扱う問題を提供する |

### 4.2 認証機能
| ID | 要件 |
|---|---|
| F-10 | ユーザーはID（メールアドレス等）とパスワードで新規登録・ログインができる |
| F-11 | 登録済みユーザーはパスキー（WebAuthn）を追加登録できる |
| F-12 | パスキー登録後は、ID+パスワードに加えてパスキーでのログインが選択できる |
| F-13 | パスワードはWorkers上でソルト付きハッシュ化して保存し、平文は保持しない |
| F-14 | ログインセッションはJWT等のトークンで管理し、有効期限を設ける |
| F-15 | パスキーの複数デバイス登録に対応する |

### 4.3 進捗管理機能
| ID | 要件 |
|---|---|
| F-20 | ユーザーごとに問題の正誤・完了状況をD1に保存する |
| F-21 | ユーザーは自分の学習進捗（コース単位・問題単位）を確認できる |
| F-22 | 未ログイン状態でも学習は可能とし、ログイン時に進捗を保存する（ゲストモード、任意） |

### 4.4 コンテンツ管理機能
| ID | 要件 |
|---|---|
| F-30 | 問題データ（テーブル定義、初期データ、模範解答、期待結果）をD1またはJSON静的ファイルで管理する |
| F-31 | 管理者は問題の追加・編集ができる（管理画面は将来スコープ／初期はDB直接投入でも可） |

## 5. 非機能要件

| 区分 | 要件 |
|---|---|
| パフォーマンス | SQLエディタでの実行結果はクライアント内処理のため体感遅延なし（目標: 実行〜表示 100ms以内） |
| セキュリティ | ・パスワードは平文非保持、ハッシュ化必須<br>・WebAuthnはRP ID／Originを厳格に検証<br>・Cloudflare WAF/Rate Limitingを有効化<br>・クライアントSQL実行はブラウザ内サンドボックス内で完結し、サーバーDBへの直接アクセスは行わない |
| 可用性 | Cloudflareのグローバルネットワークにより高可用性を確保。SLAはCloudflareの提供水準に準拠 |
| スケーラビリティ | Workers/D1/KVはサーバーレスのためトラフィックに応じて自動スケール |
| コスト | 無料枠（Pages/Workers/D1/KV）内での運用開始を想定し、初期コストを最小化 |
| ブラウザ対応 | WebAuthn対応ブラウザ（最新のChrome/Edge/Safari/Firefox）を想定。WASM実行環境が必要 |
| モバイル対応 | スマートフォン（iOS Safari / Android Chrome）でも学習可能なレスポンシブUIとする。SQL入力のしやすさを重視した専用UXを設計する（詳細は9.7参照） |
| アクセシビリティ | 学習コンテンツのコントラスト比・キーボード操作対応を考慮 |

## 6. 認証フロー詳細

### 6.1 ID+パスワード登録・ログイン
1. ユーザーがID（メールアドレス）とパスワードを入力
2. Workers APIがパスワードをハッシュ化（Web Crypto APIのPBKDF2等）しD1に保存
3. ログイン時はハッシュ照合し、成功時にJWTを発行、KVにセッション情報を記録

### 6.2 パスキー登録（WebAuthn Registration）
1. ログイン済みユーザーが「パスキー登録」を実行
2. Workers（`@simplewebauthn/server`）がChallengeを発行
3. ブラウザの`navigator.credentials.create()`でパスキー生成
4. 公開鍵・Credential IDをD1に保存

### 6.3 パスキーログイン（WebAuthn Authentication）
1. ユーザーがID入力またはパスキー選択でログイン開始
2. WorkersがChallengeを発行
3. ブラウザの`navigator.credentials.get()`で認証
4. Workersが署名を公開鍵で検証し、成功時にJWT発行

## 9. 検討事項の詳細設計

### 9.1 パスキー未対応ブラウザ・デバイスへのフォールバックUX

**方針：ID+パスワードを常時の主導線とし、パスキーは対応環境でのみ「追加の選択肢」として出す。**

| 項目 | 内容 |
|---|---|
| 対応判定 | `window.PublicKeyCredential`の存在有無でWebAuthn対応をfeature detect。加えて`PublicKeyCredential.isConditionalMediationAvailable()`でConditional UI（自動入力型パスキーUI）対応も判定 |
| 非対応ブラウザ | パスキー関連ボタン・導線を非表示にする（グレーアウトではなく非表示。「使えない機能を見せて迷わせない」を優先）。ログインはID+パスワードのみ提示 |
| 対応ブラウザ・未登録ユーザー | ログイン画面はID+パスワード入力欄をデフォルト表示しつつ、Conditional UI対応環境ではID欄フォーカス時にOS標準のパスキー選択候補を自動表示（Chrome/Safariの挙動に準拠） |
| 途中失敗時のフォールバック | パスキー認証がユーザーキャンセル・タイムアウト・エラーになった場合、自動的にID+パスワード入力フォームへ切り替える（エラーで詰ませない） |
| 複数デバイス間 | 別デバイス（PC）からのログイン時にスマホのパスキーを使う「ハイブリッド転送（QRコード）」はWebAuthn仕様の標準機能のため追加実装は不要。ただしWebAuthn自体非対応の古いブラウザではこの手段も使えないため、その場合はID+PWのみに誘導 |
| 登録済みだが端末変更 | パスキーを紛失・機種変更した場合に備え、ID+パスワードでのログインを恒久的な代替手段として維持する（パスキーのみのアカウントにはしない） |

### 9.2 問題コンテンツの管理画面（CMS）の要否・スコープ

**方針：MVPでは管理画面を作らず、Gitベースのコンテンツ管理を採用。CMSは将来スコープとし、着手条件を明文化する。**

| フェーズ | 方式 |
|---|---|
| MVP | 問題データ（`schema_sql` / `seed_sql` / `expected_result`等）をリポジトリ内にJSON/YAMLで管理し、PRレビュー後にCI/CDでD1へ投入するマイグレーションスクリプトを実行。管理画面は不要 |
| 将来（着手条件） | 「月間の問題追加数が一定数（目安50件）を超える」「非エンジニアのコンテンツ担当者が編集する必要が生じる」のいずれかを満たした時点で管理画面を検討 |
| 将来実装案 | Cloudflare Accessで保護した内部限定の管理用Workersルートに、問題のCRUD機能を持つ簡易UIを追加（認証はCloudflare Access側に委譲するため自前の権限管理は不要） |

理由：初期段階で管理画面に投資すると開発コストが先行するため、Gitワークフロー（バージョン管理・レビュー・ロールバックが標準機能として付随）で十分に運用可能と判断。

### 9.3 クライアントサイドSQLite実行時のパフォーマンス

**方針：問題ごとのデータ規模に上限を設け、大規模データを扱う問題は別方式を検討する。**

| 項目 | 内容 |
|---|---|
| 想定リスク | `sql.js`はDB全体をWASMのメモリ上に展開して動作するため、行数が多いデータセット（目安：数万行以上）では初期ロード・クエリ実行が重くなる可能性がある |
| 基本方針 | 通常の学習問題は**1テーブルあたり数千行程度（目安5,000行以下）**に収め、ブラウザ内実行で十分な速度を確保する |
| 大規模データを扱いたい問題（インデックス設計・パフォーマンスチューニング系） | `wa-sqlite` + OPFS（Origin Private File System）VFSへの切り替えを検討。ファイルベースの非同期I/Oとなり、`sql.js`のオンメモリ方式より大きなデータを扱いやすい。ただしOPFS対応はブラウザ依存のため対応状況を要確認 |
| 読み込み高速化 | WASMバイナリ・問題データはCache API（Service Worker）でキャッシュし、2問目以降の遷移を高速化する |
| 計測 | リリース前に代表的なクエリ（JOIN・GROUP BY・サブクエリ等）×代表的な行数でベンチマークを実施し、体感遅延の閾値（目標100ms〜数百ms）を超える構成は問題設計時点で回避する運用ルールとする |

### 9.4 不正解時のヒント・解説機能

**方針：学習継続率に直結するため「あり」とし、MVPから段階的ヒント＋模範解答解説を実装する。**

| 項目 | 内容 |
|---|---|
| ヒント | 問題ごとに段階的ヒント（例：3段階）をJSON配列として`problems`テーブルに保持し、ユーザーが任意タイミングで1段階ずつ開示できるようにする |
| 解説 | 不正解が一定回数続いた場合、または「答えを見る」ボタン押下時に、模範解答SQLと解説文を表示する |
| データ設計への反映 | `problems`テーブルに`hints`（JSON）、`explanation`（TEXT）カラムを追加 |
| 利用状況の記録 | ヒント使用有無・使用段階を`progress`テーブルまたは別途ログとして記録し、将来の問題難易度調整の材料とする（任意・将来スコープ） |

### 9.5 多言語対応の要否

**方針：MVPは日本語のみ。ただしUI文言とコンテンツを分離し、将来の多言語化コストを抑える設計だけ先に行う。**

| 項目 | 内容 |
|---|---|
| MVPスコープ | UI・問題文とも日本語のみ提供 |
| 将来拡張への備え | UI文言は`react-i18next`等のi18nライブラリ経由で管理し、ハードコーディングしない。問題文・解説文は`problems`テーブルに`locale`カラムを持たせる設計とし、将来的に多言語レコードを追加できるようにしておく |
| 判断根拠 | 初期からの多言語翻訳・運用コストは大きい一方、i18n対応の「器」だけ用意しておくコストは小さいため、器のみ先行整備する |

### 9.6 ゲスト利用時の進捗のログイン後引き継ぎ

**方針：ゲスト進捗はブラウザのlocalStorageに保持し、ログイン/新規登録成功時に1回限りのマイグレーションAPIでD1へ統合する。**

| 項目 | 内容 |
|---|---|
| ゲスト時の保存先 | `localStorage`に`{ problem_id, status, last_submitted_sql, updated_at }`の配列を保持（機微情報は含まないため localStorage で問題ない） |
| ログイン/登録成功時 | クライアントがlocalStorageの進捗データをWorkers APIへ送信し、サーバー側でD1の`progress`テーブルにマージする |
| マージ方針 | 同一`problem_id`について、①D1に記録が無ければゲスト進捗を新規登録、②D1に既存記録がある場合は「正解」を優先するステータスを採用（どちらかが正解済みなら正解扱い）。SQL本文の食い違いはユーザーへの確認は行わず、より新しい`updated_at`側を採用する簡易ルールとする |
| マイグレーション後 | 統合が完了したらlocalStorageのゲスト進捗はクリアする |
| 備考 | 複雑な競合解決UI（ユーザーに選ばせる等）はMVPでは実装せず、上記の自動ルールのみで運用する |

### 9.7 スマホ対応（レスポンシブ / モバイルUX）

**方針：レスポンシブ対応を必須とし、特に「SQLをスマホで打ちやすくする」点を最優先で設計する。**

学習アプリの性質上、通学・通勤中などのスキマ時間利用が想定されるため、スマホ対応はUX上の優先度が高い。一方でSQLはキーボード入力が主体の言語であり、フリック入力での記号（`,` `(` `)` `'` `;` `=` 等）入力は負担が大きい点が最大の課題となる。

| 項目 | 内容 |
|---|---|
| 画面構成 | PC版はエディタ／結果／スキーマ情報を同時表示するが、スマホでは**タブ切り替え型**（「エディタ」「結果」「テーブル定義」）にレイアウトを変更し、各エリアを画面幅いっぱいに使えるようにする |
| SQL入力支援ツールバー | エディタ上部に、よく使うキーワード・記号（`SELECT` `FROM` `WHERE` `JOIN` `GROUP BY` `ORDER BY` `,` `(` `)` `;` 等）をワンタップで挿入できるツールバーを設置し、フリック入力の手間を軽減する |
| テーブル名・カラム名補完 | 現在の問題で使えるテーブル名・カラム名をタップ挿入できる候補パネルを表示し、タイプミスを減らす（CodeMirror 6の自動補完機能を活用） |
| キーボード表示時のレイアウト | ソフトウェアキーボード表示中は結果表示エリアが隠れるため、「実行」ボタン押下時に自動でキーボードを閉じ、結果エリアへスクロールする挙動とする |
| タッチターゲットサイズ | ボタン・タブ等のタップ領域は44px四方以上を確保する（iOS Human Interface Guidelines準拠） |
| パスキーとの相性 | スマホは顔認証・指紋認証（Face ID / Touch ID / Android生体認証）とWebAuthnの相性が非常によく、PCよりむしろ快適なUXになりやすい。モバイル検出時はログイン画面でパスキーによるログインを優先的に訴求する |
| パフォーマンス | 低スペック端末を考慮し、WASMバイナリの初期ロード時間・メモリ使用量を実機検証する。Service Workerによるキャッシュで2回目以降の起動を高速化する |
| レイアウト実装方針 | モバイルファーストでCSSを設計し、Tailwind CSS等のブレークポイント機構を用いてPC/タブレット/スマホの3段階に対応する |
| 対象デバイス・ブラウザ | iOS Safari（最新2バージョン）、Android Chrome（最新2バージョン）を主要な動作確認対象とする |

## 11. 開発プロセスとドキュメント管理（ウォーターフォール）

### 11.1 開発プロセス
本プロジェクトは**ウォーターフォール型**の開発プロセスで進行する。各フェーズの成果物（設計書）はリポジトリ内の`docs/`配下に必ず作成し、レビュー・承認を経て次工程に着手するフェーズゲート運用とする。

```
要件定義 → 基本設計（外部設計） → 詳細設計（内部設計） → 実装 → テスト → リリース
```

### 11.2 フェーズ別必須成果物

| フェーズ | 成果物 | 格納先（例） | 記載内容の目安 |
|---|---|---|---|
| 要件定義 | **要件定義書**（本書） | `docs/requirements.md` | 本書の内容一式（機能要件・非機能要件・アーキテクチャ・認証設計等） |
| 基本設計（外部設計） | **画面定義書** | `docs/screen-design.md` | 画面一覧、画面遷移図、各画面のワイヤーフレーム、画面項目定義（入力/表示項目、バリデーションルール）、レスポンシブ（PC/タブレット/スマホ）ごとのレイアウト差異 |
| 基本設計（外部設計） | **DB定義書** | `docs/db-design.md` | ER図、テーブル定義書（論理名・物理名・型・NULL可否・制約・インデックス）、D1マイグレーションファイルとの対応表 |
| 詳細設計（内部設計） | **処理設計書** | `docs/process-design.md` | 機能ごとのシーケンス図／フローチャート、API仕様（エンドポイント・リクエスト/レスポンス形式）、認証処理（ID/PW・WebAuthn）の内部ロジック、クライアントサイドSQL実行処理の内部フロー |
| テスト設計 | **テスト仕様書**（単体・結合を含む） | `docs/test-spec.md` | 単体テスト仕様書（関数・コンポーネント単位のテストケース一覧）、結合テスト仕様書（フロント⇔Workers API、Workers⇔D1、クライアントSQLエンジンの結合ケース）、総合テスト観点（必要に応じて別紙化） |

### 11.3 運用ルール
- 上記4種の設計書（画面定義書／DB定義書／処理設計書／テスト仕様書）は、**各対応フェーズの完了条件として必須作成**とする（作成なしでの次工程着手は不可）
- テスト仕様書は「単体テスト」「結合テスト」を必ず区別して記載し、両方の観点を含めること
- 各設計書は本要件定義書との整合性を保つこと。要件定義書側に変更が入った場合は、影響する設計書も追随して更新する
- `docs/`配下のファイル構成・命名は上表を初期案とし、プロジェクト開始時に確定させる
